# Internationalisation (i18n) — Design Spec

**Date:** 2026-05-28  
**Status:** Approved  
**Stack:** Next.js 16 App Router · next-intl · TypeScript

---

## Goal

Add French/English language support to the portfolio with URL-based locale switching (`/fr/...` and `/en/...`). Architecture must scale to future content additions and new languages with minimal friction.

---

## Architecture

### Folder structure

```
app/
  [lang]/
    layout.tsx          ← locale-aware root layout (html lang attr, next-intl provider)
    page.tsx
    about/page.tsx
    projects/page.tsx
    projects/[slug]/page.tsx
    contact/page.tsx
    not-found.tsx
  layout.tsx            ← minimal HTML shell, no locale logic
middleware.ts           ← Accept-Language detection + redirect / → /fr or /en

dictionaries/
  fr.json
  en.json

lib/
  i18n.ts               ← supported locales, default locale (fr), getDictionary(locale)
```

### Locale config (`lib/i18n.ts`)

```ts
export const locales = ['fr', 'en'] as const
export type Locale = typeof locales[number]
export const defaultLocale: Locale = 'fr'
```

Adding a new language in the future: add a JSON file to `dictionaries/`, add the locale key to `locales`.

---

## Routing & Middleware

- `middleware.ts` intercepts **all** requests without a locale prefix (not just `/`)
- Reads `Accept-Language` header, matches against supported locales
- Redirects to `/fr` (default) or `/en`
- Old bookmarks (`/about`, `/projects`, etc.) are caught by the same middleware and redirected to `/fr/about`, `/fr/projects`
- The URL is the single source of truth for locale — no cookie, no localStorage

## Page Migration Pattern

Each page becomes an async Server Component that loads the dictionary and passes strings to client components as props.

```tsx
// app/[lang]/about/page.tsx
export default async function AboutPage({ params }: { params: { lang: string } }) {
  const t = await getDictionary(params.lang)
  return <AboutPageContent t={t.about} />
}
```

Client components receive translated strings as props — they have no knowledge of the active locale.

**Files that change:**

| File | What changes |
|---|---|
| `app/[lang]/layout.tsx` | Dynamic `lang` on `<html>`, next-intl provider wrapping |
| `app/[lang]/page.tsx` | Loads `t.home`, passes to section components |
| `app/[lang]/about/page.tsx` | All inline strings extracted to JSON |
| `app/[lang]/projects/page.tsx` | UI labels from JSON, project data stays in TS |
| `app/[lang]/projects/[slug]/page.tsx` | UI strings from JSON |
| `app/[lang]/contact/page.tsx` | Form labels from JSON |
| `components/layout/Header.tsx` | `navLinks` from `t.nav`, adds `LanguageSwitcher` |
| `components/sections/HeroSection.tsx` | Receives `t` as props |
| `components/sections/FeaturedProjects.tsx` | Receives `t` as props |
| `components/sections/SkillsSection.tsx` | Receives `t` as props |
| `lib/data/projects.ts` | Keeps slug/stack/links — text descriptions move to JSONs |

**Files that don't change:** UI primitives (`Badge`, `Button`, `AnimatedSection`, etc.), styles, animations, theme logic.

## SEO Metadata

Static `export const metadata` becomes dynamic `generateMetadata({ params })` on every page. Each page loads the dictionary and returns locale-specific title/description/openGraph.

```tsx
export async function generateMetadata({ params }: { params: { lang: string } }): Promise<Metadata> {
  const t = await getDictionary(params.lang)
  return {
    title: t.about.meta.title,
    description: t.about.meta.description,
    openGraph: { locale: params.lang === 'fr' ? 'fr_FR' : 'en_US', ... }
  }
}
```

## Language Switcher Component

Located in `Header`, next to `ThemeToggle`. Reads the current locale from the pathname, generates a link to the same path in the other locale.

```
[FR | EN]  ← active locale highlighted, other is a link
```

- No state needed — derives locale from `usePathname()`
- On switch: replaces the first path segment (`/fr/about` → `/en/about`)
- Supports any number of locales (maps over `locales` from `lib/i18n.ts`)

---

## Constraints & Non-Goals

- No server-side locale persistence (cookie/session) — URL is the source of truth
- No automatic content translation — all strings must be manually provided in both JSONs
- Project technical data (stack badges, links) is not translated — only UI text and descriptions
- No RTL support needed
